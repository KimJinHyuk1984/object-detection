# 4차시 교사용 진행안
주행 인식 앱을 검증하고 공유하기 · 50분

[강의 페이지](../video-app/index.html) · [활동지 PDF](../files/lesson-04-workbook.pdf) · [캡처 안내](lesson-04-capture-guide.md) · [공유 준비](lesson-04-sharing-guide.md)

## 수업 목표와 제출물
학생은 학습에 쓰지 않은 영상에서 성공·실패를 구분하고, 같은 장면의 표시 조건을 비교하며, 근거를 들어 개선 계획을 설명합니다. 제출물은 활동지 3쪽과 성공·실패 PNG 2장입니다. 신뢰도 비교 PNG 2장과 공유 확인 PNG 1장은 수업 기록용으로 함께 보관합니다.

`line`은 도색된 차선이 아닌 **차선 사이의 주행 가능한 도로 영역**입니다. 신뢰도 퍼센트를 정확도로 읽지 않습니다. 앱의 신호 안내는 감지 결과를 설명하는 학습용 출력입니다.

## 수업 전 준비
- [ ] 3차시 실습 ZIP을 풀고 Python 3.11 또는 3.12에서 앱을 실행합니다. 설치는 수업 전에 마칩니다.
- [ ] Workspace·Workflow와 그 안에서 실제 사용하는 분할 모델의 프로젝트/버전을 기록합니다. API 키는 활동지·캡처·저장소에 넣지 않습니다.
- [ ] 학습·설정 조정에 쓰지 않은 별도 촬영 영상을 준비합니다. source.mp4의 인접 프레임은 독립적인 새 영상으로 취급하지 않습니다.
- [ ] 성공·실패를 관찰할 재생 시각을 미리 찾습니다. 3분 영상 전체를 사용할 수 있지만, 수업에서는 비교할 장면을 정해 시간을 확보합니다.
- [ ] 객체 박스·line 마스크·신호 안내를 실제 MODEL RESULT에서 확인합니다. 초록·빨강·노랑·색 불명 신호가 영상에 없으면 관찰하지 못했다고 기록합니다.
- [ ] 동일한 영상·모델·배치 8장 조건으로 초당 2회/5회 분석을 각각 끝내고 걸린 시간을 측정합니다. 실제 측정값과 계산 예시를 구분합니다.
- [ ] 공유 방식 A(교사가 준비한 실제 배포 주소) 또는 B(별도 PC의 같은 ZIP 실행)를 선택하고 사전 시험합니다. A가 준비되지 않았으면 B로 진행합니다.
- [ ] [캡처 목록](lesson-04-capture-guide.md)을 확인하고 활동지 3쪽을 인쇄합니다.

사용자는 현재 앱이 잘 동작한다고 확인했습니다. 이는 모든 영상의 정확도·도로 마스크 품질·외부 배포 완료를 보장하는 평가 자료는 아닙니다.

## 50분 운영
| 시간 | 교사 진행 | 학생 활동·확인 |
| --- | --- | --- |
| 0–5분 | 성공·실패의 기준과 오늘의 결과물을 소개 | 활동지 1쪽에 객체/영역/신호 확인 기준 선택 |
| 5–8분 | 새 영상과 공통 설정 확인 | 영상명, 길이, Workflow, 모델 버전 기록 |
| 8–16분 | 분석·재생을 지도하고 결과 대기/실패를 구분 | MODEL RESULT에서 성공·실패 장면 각각 찾기 |
| 16–20분 | 캡처와 관찰 기록 점검 | 성공·실패 PNG 저장, 시각·현상 기록 |
| 20–26분 | 같은 장면을 일시정지하고 신뢰도 40%/70% 비교 | 2쪽 비교표와 PNG 2장 기록 |
| 26–30분 | 준비한 초당 2회/5회 분석 자료 제시 | 이미지 수·실측 시간·표시 간격 비교 |
| 30–40분 | A 또는 B 방식의 공유 체험 | 3쪽에 실제 방식·결과·남은 문제 기록 |
| 40–43분 | 근거를 바탕으로 발표 문장 정리 | 성공, 실패, 개선 계획 작성 |
| 43–47분 | 짝끼리 60초 발표 후 피드백 | 발표와 근거 일치 여부 확인 |
| 47–50분 | 2–3팀의 핵심 사례만 전체 공유 | 활동지·캡처 제출, 다음 행동 한 문장 |

### 비교를 공정하게 하는 방법
학생 비교는 **같은 영상·같은 재생 시각·같은 Workflow/모델·같은 분석 결과**를 사용합니다. 분석한 장면에서 일시정지하고 신뢰도만 40% → 70%로 바꿉니다. 모든 클래스 선택과 마스크 불투명도도 동일하게 유지합니다. 이 변경 자체는 재추론을 일으키지 않습니다. 기존 분석이 진행 중이면 다른 구간의 API 요청은 계속될 수 있으므로, 비교 장면 분석 후 분석을 중지하고 비교해도 됩니다.

신뢰도 기준을 높이면 남는 결과가 같거나 줄어듭니다. 낮은 기준은 미탐을 줄일 가능성이 있지만 오탐이 늘 수 있습니다. 이번 두 장면만으로 전체 정확도를 주장하지 않습니다. 두 조건의 결과가 같아도 유효한 관찰입니다. 서버/Workflow에서 이미 걸러진 결과는 앱 기준을 낮춰도 되살릴 수 없습니다.

분석 빈도를 바꾸면 캐시가 초기화되어 재분석해야 합니다. 10분 안에 각 모둠이 긴 영상 두 번을 분석하게 하지 않고, 교사의 사전 측정 자료로 비교합니다.
- 180초 × 2회/초 = 360장, 8장씩 약 45개 요청.
- 180초 × 5회/초 = 900장, 8장씩 약 113개 요청.
- 분석 시각 간격은 약 0.5초/0.2초이며 원본 재생 FPS와 다릅니다.
- 위 수치는 예시 계산입니다. 끝 구간·재시도·실행 범위에 따라 실제 요청 수가 다를 수 있고, 처리 시간은 실제로 측정합니다.
- 비용 수치를 추정하지 않습니다. HTTP 요청 수와 처리 이미지 수는 다릅니다.

### 오류를 해석하는 질문
1. **분석 대기인가, 결과가 있는데 놓친 것인가?** DEMO / NO RESULT / MODEL RESULT 표시를 먼저 봅니다.
2. **무엇을 놓치거나 잘못 표시했는가?** 미탐, 오탐·오분류, 영역 경계 오류, 판단 어려움 중 기록합니다.
3. **사실과 원인 추측이 분리되어 있는가?** “작은 신호등이 없었다”는 관찰, “작은 대상 학습 자료가 부족하다”는 확인 전 가설입니다.
4. **다음 실험에서 무엇을 고정할 것인가?** 모델·영상·시각을 기록하고 한 조건만 바꿉니다.

신호 안내 우선순위는 빨강 → 노랑 → 색 불명 → 초록입니다. 신호가 없을 때와 아직 분석하지 않은 상태도 구분합니다. 다른 차로의 신호일 수 있으므로 초록 감지 여부만으로 실제 주행 가능 여부를 판단하지 않습니다.

## 시간 부족·연결 문제 대응
- API가 느리면 미리 저장한 실제 결과 PNG·JSON으로 관찰 활동을 이어갑니다. 실시간 확인과 저장 자료 관찰을 기록에서 구분합니다.
- 적절한 실패 장면을 못 찾으면 관찰 구간과 “이 구간에서 실패 미발견”을 기록합니다. 오류를 만들어내거나 정확도 100%라고 결론 내리지 않습니다. 교사의 실제 실패 사례를 추가 관찰할 수 있습니다.
- line이 없으면 선택 필터·신뢰도·응답의 points·Workflow의 분할 모델을 순서대로 확인합니다. 박스 모델을 도로 분할 성공 사례로 소개하지 않습니다.
- 배포 URL이 없으면 B 방식으로 전환합니다. 다른 PC에서 실행한 것은 재현 확인이며 외부 배포 완료가 아닙니다.
- 재학습과 추가 배포 작업은 후속 과제로 남깁니다. 학생 발표 시간을 확보합니다.

## 피드백 기준
각 항목을 충족/보완 필요로 표시합니다.
- 조건: 영상·시각·Workflow/모델 버전이 있어 다시 확인할 수 있다.
- 근거: 성공·실패 설명이 캡처의 실제 결과와 일치한다.
- 비교: 한 조건만 바꾸었고 신뢰도와 정확도를 구분한다.
- 개선: 관찰과 가설을 구분하고 검증할 다음 행동이 구체적이다.
